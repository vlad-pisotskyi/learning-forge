# learning-forge

## What this repo is

Two layers. Keeping them separate is the point.

**Layer 1 — the Forge.** A general-purpose machine that turns a topic name into a
complete self-teaching program: a researched and cited chapter sequence, practical
challenges with hidden evaluation sets, and a Teacher, Helper, and Judge scoped to
that subject. The Forge is topic-agnostic. It lives in `.claude/skills/`,
`.claude/agents/`, `contract/`, and `tools/`. No subject knowledge belongs in it.

**Layer 2 — a topic instance.** One directory under `topics/` holding a single
subject's material. Generated by the Forge, never hand-authored.

Layer 1 comes first, then produces Layer 2. If the Forge cannot generate a topic
without manual patching, the Forge is the bug. Fix it there and regenerate.

## Who the learner is

A strong TypeScript engineer, comfortable in JavaScript, learning Python, new to
the subject being taught. They know Claude can write the code for them; that is
exactly what they do not want.

**The repo teaches and grades. It never solves.** No agent in this repo writes
challenge code for the learner, and none reveals a reference solution or an
evaluation set. Where that rule is enforced by the harness rather than by wording,
the enforcement is the guarantee and the wording only explains why.

## Layout

```
contract/     the topic contract: spec + fixtures. Read this before generating.
tools/        the validator and other Forge scripts (TypeScript, Node 22+)
topics/<slug>/  one generated topic instance
.claude/rules/  path-scoped rules; they load only when a matching file is touched
```

Full directory shape, file-by-file, is in `contract/TOPIC-CONTRACT.md`. Do not
reconstruct it from memory or from what happens to exist on disk.

## Hard content rules

**Every non-obvious claim carries a citation marker.** The marker resolves to an
excerpt in the topic's `sources.json` carrying a URL, the exact quoted passage the
claim rests on, and the date it was retrieved. A claim with no marker, or a marker
whose quoted passage does not actually support it, is a defect and fails
verification. Paraphrase in the prose; quote exactly in the source entry.

**Chapters state facts, not hedges.** No "may", "might", "some argue", "it is
generally considered". If something is genuinely contested in the field, the
chapter says it is contested and cites both sides — that is itself a fact and is
allowed. Hedging used to cover thin research is not.

These two rules pull against each other on purpose. Confident prose plus a pinned
quote for every claim means the confidence has to be earned before it is written.

## The three roles

Every topic gets all three, scoped to that topic's directory so inactive topics
cost nothing at session start.

**Teacher.** Works through one chapter at a time: the learner reads the prose, the
Teacher answers what they ask, quizzes them, and records progress. Loads the current
chapter and the learner's recorded weak concepts, never the whole book. It asks the
quiz questions without holding the answers — the key lives in `quizzes/.hidden/` and
is read only by a grader that never saw the lesson.

**Helper.** Available during challenges. Explains concepts, reframes the problem,
asks leading questions, points at the chapter that covers the confusion. Cannot
write code and cannot hand over a working answer. Runs as a subagent with write
tools removed, so this holds regardless of what the model decides to do.

**Judge.** Runs after a submission. Executes the hidden evaluation set, reports the
numbers, then scores the submission against a written rubric and names what should
have been there. Runs isolated so only its verdict reaches the learner's
conversation.

## Token discipline

A stated requirement, not a preference. An earlier planning session burned a
session limit in ten minutes by fanning out four unbounded research agents at once.

- This file stays under 200 lines. It loads in full at every session start.
- Anything narrow goes in `.claude/rules/*.md` with a `paths:` glob. Those cost
  nothing until a matching file is touched.
- Skill descriptions are the recurring cost, since every description loads at
  startup. Keep them one tight sentence. Skill bodies load on invocation, so put
  detail there, and push heavy reference material into files the body reads on
  demand.
- Per-topic skills live in `topics/<slug>/.claude/skills/`. They load the first
  time a file in that topic is touched, so a repo with ten topics costs the same
  at startup as a repo with one.
- Anything that reads a lot of material goes to a subagent, so only the conclusion
  comes back into the parent context.
- Fan-out work checkpoints to `.forge-cache/` after each shard. A dead agent must
  cost one shard, never the run.
- `@path` imports in this file do not defer. Imported content loads at launch with
  its parent. Do not use imports to pretend this file is shorter than it is.

## Generating a topic

The `forge-generate` skill runs it, one stage per invocation: research, map,
apply, chapters, challenges. The map stage stops for approval before any prose
exists. `npm run forge -- status <slug>` says where a topic is and what it still
owes, read off disk, so a run survives a dead session.

Structure is the CLI's, content is the model's. `npm run forge` writes the tree, the
source ids, the manifests, chapter frontmatter, quiz shells, and the three role skills
stamped from templates; agents write prose, excerpts, questions, briefs, and code.
Never hand-author a file the CLI generates — revise the map or the template and apply
it again.

Read `contract/TOPIC-CONTRACT.md` in full before generating. Generated material is
checked mechanically, not by eye:

```
npm run validate -- topics/<slug>      # one topic
npm run validate:all                   # every topic
```

A topic that fails the validator is not done. Both verification agents — the
pedagogical critique and the faithfulness auditor — run after the validator
passes, not instead of it.

## What is committed and what is not

Chapters, sources, challenge briefs, rubrics, quiz answer keys, hidden evaluation
sets, and reference solutions are committed. They are the material.

Learner progress (`topics/*/.state/`) and learner attempts
(`topics/*/challenges/*/work/`) are local-only and gitignored. Anyone can clone
this repo and start clean.

`.hidden/` is hidden from agents, not from people. The evaluation set and the
reference solution are committed, so anyone reading this public repo can open them,
and that is fine — the material is ordinary published knowledge and the learner owns
the repo. What the boundary buys is that no agent hands them over mid-challenge: the
Teacher and Helper cannot read `.hidden/` at all, and the Judge reads it in an
isolated context that returns a verdict and nothing else. Deciding to look is the
learner's to make deliberately; it should never happen because a model was asked a
leading question.

The read boundary is currently stated in each role's own instructions rather than
enforced by the harness. Tool lists restrict tools, not paths, so "no reading
`.hidden/`" becomes real in Phase 5, as a hook. What is already mechanical is the
Helper having no write tools and the graders running in isolated contexts.

## The repo is public

Committed material contains nothing personal. No names, emails, tokens, keys,
internal hostnames, or anything taken from a private system. Sources cite publicly
reachable URLs and quote published text.

The one category of personal data this repo produces — what the learner answered,
scored, and got wrong — is gitignored (`topics/*/.state/`,
`topics/*/challenges/*/work/`), so it stays off GitHub by default rather than by
anyone remembering. Do not add either path to a commit, and do not quote their
contents into a chapter, a commit message, or an issue.
